# Пояснення проєкту для координатора курсової роботи

## 1. Загальна ідея

Цей проєкт є прототипом власної CI/CD-платформи для опису, запуску та аналізу процесів безперервної інтеграції й доставки програмного забезпечення.

CI/CD-системи використовуються командами розробників для автоматичного запуску перевірок, тестів, збірок, пакування та інших дій після змін у коді. Типові приклади таких систем: GitHub Actions, GitLab CI/CD, Buildkite. У більшості з них робочі процеси описуються у конфігураційних файлах, часто у форматі YAML, а перевірка змін зазвичай відбувається через віддалений запуск.

Ідея цього проєкту полягає в іншому підході: робочі процеси мають описуватися у TypeScript, тобто у звичному для розробників кодовому середовищі, а виконуватися вони мають власним рушієм проєкту. Система задумана як локально-орієнтована і самостійно розгортувана CI/CD-платформа: користувач може розробляти та перевіряти workflow локально, а потім запускати ті самі workflow у self-hosted середовищі.

## 2. Яку проблему вирішує проєкт

У багатьох сучасних CI/CD-системах розробка workflow залишається незручною. Автор змінює конфігурацію, пушить зміни або запускає віддалений процес, чекає результату, читає логи, виправляє помилки й повторює цикл. Це повільно, особливо коли помилка стосується не самого коду продукту, а логіки CI/CD-процесу.

Інша проблема полягає у фрагментації логіки. Частина поведінки описується в YAML, частина в shell-скриптах, частина в окремих actions або зовнішніх інструментах. Через це workflow важко читати, змінювати, тестувати та пояснювати.

Цей проєкт пропонує зробити workflow ближчим до звичайної розробки програмного забезпечення: описувати його в TypeScript, використовувати повторне використання й композицію, запускати локально та отримувати структуровану інформацію про те, що саме виконувалося, чому воно виконувалося і де сталася помилка.

## 3. Основна мета

Мета проєкту — створити прототип code-first CI/CD-системи, у якій workflow:

- описуються у власній TypeScript DSL;
- перетворюються на нормалізоване визначення workflow;
- плануються власним Engine;
- виконуються як набір ізольованих execution units;
- мають зрозумілий стан виконання, історію подій, логи й артефакти;
- можуть запускатися локально і в self-hosted режимі за однаковою моделлю.

Тобто проєкт не є просто обгорткою над GitHub Actions або GitLab CI/CD. Він моделює власну CI/CD-платформу з власним способом опису workflow, власним рушієм виконання та власними поверхнями керування й інспекції.

## 4. Для кого призначений продукт

Цільовий користувач — інженер або команда, які створюють і підтримують CI/CD-процеси. Це люди, яким важливо швидко перевіряти зміни у workflow, бачити структуру виконання, розуміти залежності між кроками та мати контроль над середовищем виконання.

У навчальному контексті цей проєкт демонструє не лише створення окремого інструмента, а й проєктування повноцінної програмної системи з архітектурними межами, відповідальністю підсистем, моделлю стану та еволюційним шляхом від прототипу до більш складної платформи.

## 5. З чого складається система

Архітектурно система поділена на три основні шари.

### DSL

DSL відповідає за те, як користувач описує workflow. У цьому проєкті workflow є TypeScript-native, тобто автор використовує TypeScript не для безпосереднього виконання CI/CD-логіки, а для декларативного опису структури workflow.

DSL дозволяє описувати workflow, execution units, залежності, входи, виходи, артефакти, звіти, умови виконання та політики на кшталт retry або timeout. Важливо, що DSL не виконує workflow самостійно і не створює execution plan. Його завдання — зібрати авторський опис і матеріалізувати його у нормалізоване визначення workflow, яке вже може прийняти Engine.

### Engine

Engine є центральною підсистемою виконання. Він отримує нормалізоване визначення workflow, перевіряє його, створює явний execution plan, запускає workflow run, визначає готовність execution units, передає їх на ізольоване виконання, оновлює поточний стан і записує історію виконання.

Engine поділений на кілька внутрішніх відповідальностей: Planner, Orchestrator, Executor, State Store, Event Log та Artifact Store. Такий поділ потрібен, щоб не змішувати планування, виконання, збереження стану, історію подій і роботу з артефактами.

### Interface

Interface — це поверхні взаємодії користувача із системою, наприклад CLI або dashboard. Вони не повинні напряму читати внутрішні сховища Engine. Замість цього Interface працює через Engine-owned control and inspection contract: запускає, скасовує або переглядає workflow через узгоджені операції рушія.

## 6. Чому важлива TypeScript DSL

Використання TypeScript як мови опису workflow дає змогу наблизити CI/CD-конфігурацію до звичайної інженерної роботи. Розробники можуть використовувати знайомі принципи структурування: функції, композицію, повторне використання фрагментів, константи та статичну генерацію схожих частин workflow.

Водночас TypeScript у цьому проєкті не використовується як довільна runtime-мова для керування виконанням. Це принципова межа. У прототипі workflow має бути статичним DAG: усі execution units і залежності між ними відомі до початку виконання. Це потрібно для передбачуваності, інспекції та надійного планування.

Таким чином, DSL дає зручність code-first підходу, але не руйнує статичну й зрозумілу модель виконання.

## 7. Чому потрібен власний Engine

Власний Engine потрібен, бо продукт не позиціонується як надбудова над існуючими CI/CD-системами. Він має власну модель workflow, власні правила виконання та власне уявлення про стан.

Engine відповідає за те, щоб workflow не просто запускалися як набір команд, а були зрозумілими для системи. Він знає структуру workflow, залежності, поточний стан кожного execution unit, історію переходів, результати, помилки, логи та артефакти.

Це дозволяє робити інспекцію workflow не лише через сирі логи, а через структуровану модель: які частини workflow вже виконані, які заблоковані, які впали, які залежності задоволені, які артефакти були створені.

## 8. Модель виконання прототипу

Прототип має свідомо обмежену модель виконання. Workflow є статичним DAG. Перед запуском Engine створює явний execution plan. Після цього Orchestrator поступово визначає, які execution units готові до запуску, і передає їх Executor.

Executor запускає execution units в ізольованому контейнерному середовищі. Він не приймає рішень про залежності, retry, cancellation або фінальний результат workflow. Його роль — виконати конкретну одиницю роботи й повернути нормалізований результат: статус, логи, outputs, metadata артефактів і локальну інформацію про помилки.

Це розділення важливе, бо Orchestrator відповідає за семантику workflow, а Executor — лише за ізольоване виконання. Такий підхід залишає можливість у майбутньому перейти від single-node прототипу до worker-based self-hosted або hosted моделі без зміни основної семантики Engine.

## 9. Стан, історія та артефакти

Окрема увага в проєкті приділена розділенню поточного стану, історії та payload-даних.

Поточний runtime state зберігається у State Store і є операційним джерелом істини. Саме з нього Engine розуміє, що зараз відбувається з workflow run, які units виконуються, які завершені, які заблоковані і що потрібно робити далі.

Event Log зберігає append-only історію важливих подій: створення run, запуск unit, завершення, помилки, retry, cancellation тощо. Але Event Log не є джерелом операційної істини. Прототип відновлюється не через replay подій, а через resume з поточного збереженого стану.

Artifact Store відповідає за артефакти, логи та великі outputs. Вони не вбудовуються у поточний runtime state, щоб не перевантажувати операційну модель. У state зберігаються лише посилання, metadata та короткі підсумки.

Такий поділ робить систему зрозумілішою, стабільнішою та придатнішою для майбутнього розширення.

## 10. Локальний і self-hosted режими

Одна з ключових ідей продукту — локальний і self-hosted режими мають бути режимами однієї й тієї самої системи, а не двома різними реалізаціями.

Локальний режим потрібен для швидкої розробки, перевірки й діагностики workflow на машині користувача. Self-hosted режим потрібен для запуску тієї ж моделі в середовищі, яким керує команда або організація.

У прототипі обидва режими є single-node. Це означає, що система не реалізує worker pool, distributed scheduling, remote dispatch, worker leases або hosted control plane. Таке обмеження обране свідомо: прототип має довести основну модель workflow, планування, виконання, стану та інспекції без передчасного ускладнення розподіленою інфраструктурою.

## 11. Чому проєкт має навчальну цінність

Проєкт демонструє повний цикл системного проєктування, а не лише написання коду. У ньому є:

- продуктове бачення;
- вимоги до першої версії;
- архітектурні RFC;
- ADR з прийнятими рішеннями;
- subsystem design documents;
- чіткі межі між DSL, Engine та Interface;
- продумана модель стану, історії й артефактів;
- обмеження прототипу та шлях до майбутнього розвитку.

Це робить роботу схожою на реальний інженерний проєкт, де важливо не тільки реалізувати функції, а й пояснити, чому система має саме таку форму, які рішення вже прийняті, що входить у scope, а що свідомо відкладено.

## 12. Очікуваний результат прототипу

Очікуваний результат — прототип CI/CD-системи, у якій користувач може описати workflow у TypeScript DSL, отримати нормалізоване визначення workflow, передати його в Engine, створити execution plan, запустити workflow локально або в single-node self-hosted середовищі та переглянути структурований результат виконання.

Прототип не має бути повною заміною GitHub Actions або GitLab CI/CD. Його завдання — підтвердити основну концепцію: code-first workflow authoring, власний execution engine, локальна розробка workflow, self-hosted операційна модель і workflow-aware inspection.

## 13. Межі прототипу

У межі прототипу не входять hosted control plane, managed execution infrastructure, повноцінна multi-node worker система, marketplace інтеграцій, повна мова DSL на всі майбутні сценарії або runtime graph mutation.

Ці речі можуть бути частиною майбутнього розвитку, але для курсового прототипу важливіше побудувати правильне ядро: зрозумілий DSL boundary, explicit execution plan, Engine-owned runtime semantics, current state як operational truth, event history як історію, artifact boundary і однакову модель для local та self-hosted режимів.

## 14. Підсумок

Цей проєкт — це прототип власної code-first CI/CD-платформи. Його головна ідея полягає в тому, щоб зробити workflow більш зрозумілими, локально перевірюваними та керованими, ніж у багатьох remote-first конфігураційних CI/CD-системах.

Проєкт поєднує TypeScript DSL для опису workflow, власний Engine для планування й виконання, а також майбутні Interface-поверхні для керування та інспекції. Основна цінність полягає не лише у запуску команд, а у створенні структурованої моделі workflow, яку можна аналізувати, відлагоджувати, відновлювати та розвивати.

Для курсової роботи це є прикладом системи з чіткою архітектурою, визначеними підсистемами, обґрунтованими обмеженнями прототипу та зрозумілим шляхом розвитку до повноцінної CI/CD-платформи.
